## 一、用户报的是什么（原话）

> 「手机端点击进入会话时，会话标题不能获取，回退到『新建对话』的错误兜底状态」（07:12 首次提出）
> 「我现在点进手机上我们的对话，还是显示新建任务而非标题，你可以开始定位了」（10:01 复报）

两处措辞不同（"新建对话" / "新建任务"），**页面里实际渲染的字符串是「新建任务」**
（locale key `taskList.newThread`），下文统一按「新建任务」写。

## 二、一句话结论

**打开一个「桌面端还没加载进来」的会话时，它会先落进回退态（标题「新建任务」），之后靠页面自己重试
`readSession` 成功而自愈。窗口长度 = 桌面端什么时候愿意答这次 `readSession`。**

- 冷会话首次打开：回退态，实测 **9–22 秒**自愈（任务繁忙那次约 **2 分钟**）。
- 同一个会话**第二次打开**（桌面端已加载）：**2 秒内就是正确标题**。
- 所以"刷新一下 / 重进一次就好"是必然的——它只是把第二次（热）打开提前了。

**责任边界**：页面 + 桌面端。壳侧没有干净杠杆（论证见第七节）。

读法（三条都重要）：

1. **`readSession` 的结果会翻转**：同一个 session，10:00:43 被桌面端拒（`Session is not active`），
   10:04:46 成功（1060ms）。所以问题不是"这条会话永远读不到"，而是"**还没准备好时会被拒**"。
2. **`工作区相位` 行是本轮新加的取证**（`ShellRuntime.logPhaseHistogram`，按工作区去重）：
   它证明**协议里确实有这条任务、`title` 也在**（我们自己的通知标题就来自同一份数据）。
   所以"任务列表里没有它"不成立——缺的是**页面自己那份 store 在那一刻还没填上**。
3. 同一窗口里页面在反复 `subscribeConversationV4` / `unsubscribeConversationV4` ——
   就是快照文档里那条「订阅代号守卫（runtimeRestarted）」的行为：**打开任务会把订阅拆掉重建**。

## 五、页面代码证据（这是机制的落点）

主包 `docs/05-远程网页-remote-v4-20260911/assets/index-nOVzQNKW.js`，偏移 `@345935` 附近：

```js
function R_e({workspaceAbsPath:e, activeTaskId:t, workspaceRemoteSessionId:n,

        ? u.title
        : a.formatMessage({id: u?.forkedFromTaskId ? `taskList.forkedUntitled` : `taskList.newThread`}),
```

兜底那一支（`D_e`，偏移 `@342149` 附近）：

```js
function D_e(e,t,n,r,i){
  let a = df(e,n), [o,s] = useState(null);
  useEffect(() => {
    let n = !1;
    s(e => E_e(e,t,i));
    !t || i || a.readSession({workspacePath:e, workspaceIdentity:r, sessionId:t, messageLimit:1})
      .then(e => { n || s(v_e(e)) })
      .catch(() => { n || s(null) });          // ← 失败被静默吞成 null
    return () => { n = !0 }
  }, [a,t,i,r,e]);
  return o
}
```

**关键三点**（`i` 就是调用方传进去的 `c`）：

1. `!t || i || a.readSession(...)` —— **`c`（来源 i）为真时根本不发 readSession**。
   所以正常情况下标题是走任务列表的，`readSession` 只是"列表里没有时"的兜底。
2. `.catch(() => s(null))` —— 失败被**静默吞掉**，用户看不到任何报错（也没有重试策略）。
3. `useEffect` 依赖 `[a,t,i,r,e]` —— 其中 `a = df(e,n)`、`i`、`e` 都与工作区/store 有关，
   所以**页面是靠自己 store 变化来重跑这次调用的**：这就是"自愈"的来源，也解释了为什么窗口长度
   由"下一次 store 变化 + 那一刻桌面端愿不愿意答"共同决定。

于是首次打开时的形态是：**来源 (i) 那一刻还是空**（订阅刚被拆掉重建）→ 走 (ii) → 桌面端回
`Session is not active`（这条会话还没被桌面端加载）→ 两条都空 → 标题 = `taskList.newThread` = 「新建任务」。

**`Session is not active` 这句话在页面 bundle 里搜不到**，是桌面端返回的字符串；
`README` 更早的结论「完成态任务的会话在桌面端不是 active」与本轮观测一致，
但本轮补充了一点：**"未加载"比"已完成"更接近本质**——同一条 session 稍后就能读到了。


**判据**（不用看代码）：`t2.png` 头部是「新建任务」+ 输入框「向 ZCode 提问…」= 复现成功；

所以要让窗口复现，需要一条**桌面端还没加载过**的会话（例如很久以前完成的、当天没打开过的任务）。

## 七、已经排除掉的可能性（附判据，别再重查）

| 假设 | 判据 | 结论 |
| --- | --- | --- |
| 协议里没有这条任务/没有标题 | `工作区相位 E:\Zcode_harmony：30 个任务 · running×1 …` —— 任务在，`title` 也在（我们的通知标题用的就是它） | **否定** |
| 任务列表"还没加载出来"（= 早期 README 的写法） | 更准确的说法是**页面自己那份 store 在那一刻是空的**：打开任务会拆/重建订阅（同一窗口里能看到 `unsubscribeConversationV4` + 多次 `subscribeConversationV4`） | **修正**：不是"没加载"，是"被拆了还没重建好" |
| 标题永远回退（不会自愈） | 10:02:00 截图为 `新建任务` → 10:03 同一界面已变成 `继续推进 a…`，这中间用户没做任何操作 | **否定** |
| 是"已完成任务"特有的问题 | 运行中的任务（`running×1`）**首次打开同样回退**；区别只在桌面端有没有加载过这条会话 | **否定**（"未加载"才是本质） |
| 壳的 bridge 流量把它压住了 | 窗口 9–22 秒（忙时 2 分钟），而壳一轮 burst 总共约 6.5 秒、且只在与页面共用 socket 上排队；回退也发生在壳的空闲期 | **不是主因**（壳侧争抢此前已从 3× 降到 1×，见「已知问题 D2」） |
| 通知定位那条路把它弄坏了 | 用户是**手动点**任务行复现的；壳侧 locator 那次没参与 | **否定** |
| 标题前缀改动（D15）有关系 | 把标题装饰成 `运行中 · 任务名` 只影响**通知**，与页面头部无关；而且 D15 之前这个回退就存在（更早的 README 已记） | **否定** |

## 八、还缺什么（只有桌面端能回答）

1. **`zcode-session.readSession` 对一条已完成/未加载的会话，为什么第一次拒、稍后又能读到？**
   是"拒绝触发了懒加载"，还是"有人在桌面端打开了它"？—— 这决定了修法：
   若"拒一次就会加载"，那**页面加一次带退避的重试**就能把窗口从分钟级压到秒级；
   若需要人在桌面端点开，那就得让桌面端在收到 readSession 时按需加载。
2. 桌面端的 `active` 到底指什么（正在窗口里打开？在内存里？），以及**是否可以把"手机正在看的会话"标记为 active**。
3. 页面能否在 `readSession` 失败后主动重试（现在它只依赖 store 变化被动重跑）。
